# Datasets

* [The DPV LinkML schema](dpv-linkml-schema.md) - `src/dpv/schema/`: the umbrella `dpv.yaml` over `dpv_core`, `dpv_terms` and one module of kinds per namespace family. It models DPV 2.3 under DPV's own IRIs, and `DpvCatalogue` is its tree root.
* [The core module](core-module.md) - `src/dpv/schema/dpv_core.yaml`, written by hand: the date and address types, the term status list, the classes for a vocabulary, a concept scheme, an agent, a web page and an interval, and the slots they share.
* [The terms module](terms-module.md) - `src/dpv/schema/dpv_terms.yaml`, which the converter writes: `DpvTerm` and its children `DpvConcept`, `DpvProperty` and `DpvResource`, `DpvExample`, `DpvStatement`, and one slot per DPV property under its own IRI.
* [The kinds' modules](kinds-modules.md) - The modules the converter writes with one class per kind of term, 149 in all, under each kind's own IRI: `dpv_kinds` for the core, and `dpv_pd`, `dpv_tech`, `dpv_ai`, `dpv_risk`, `dpv_legal`, `dpv_sector` and `dpv_standards`.
* [The catalogue](catalogue.md) - `src/dpv/data/`: one YAML file per namespace family, with every vocabulary, concept scheme, concept and property of DPV 2.3 as a record under its own IRI: 8,856 concepts and 307 properties.
* [The examples as data](examples.md) - `src/dpv/data/dpv-2.3-examples.yaml`: DPV's 88 examples, each with its description, and the statements of 85 of them as `DpvResource` records. Three files do not parse.
* [Where DPV's examples leave a property's usual classes](example-departures.md) - `tests/example_departures.yaml`: each place DPV's own examples use a property beyond its `rangeIncludes` or `domainIncludes`, or give a literal where the range names a class: 58 values, 65 subjects and 30 literals.
* [The contributors](contributors.md) - `src/dpv/data/dpv-2.3-agents.yaml`: the 70 people and organizations DPV's files name as contributors and creators, each with an id of the form `dpv_agent:person-<name>` or `dpv_agent:org-<name>`.
* [DPV's own mappings as SSSOM](sssom-mappings.md) - `src/dpv/mappings/`: two SSSOM sets that render the mapping files DPV publishes, 5 rows for ISO/IEC 29100:2024 terms and 24 for ODRL, each row reading with DPV's term as its subject.
* [The copy of DPV's files](upstream-copy.md) - `upstream/`: the Turtle of each vocabulary, the 88 examples, the ISO and ODRL mapping files and the licence, unchanged at the tag `dpv-2.3`. `scripts/upstream_pins.tsv` holds each of the 160 files' git object hashes.
* [The adapt copy](adapt-copy.md) - `.lokf/dpv.yaml`, which `just lokf-adapt` writes from the schema so that it can sit beside LOKF's: the file this bundle validates against, and the file a release attaches as `schema-<tag>-dpv.yaml`.
* [The neighbours' copies](neighbour-copies.md) - `tests/neighbours/`: the adapt copies 27 other lmodel repositories release, each the release's schema asset, which tests use to hold this copy's names apart from theirs.
* [The example data](example-data.md) - `tests/data/`: a valid example per class, each kind's a real record of the catalogue, a counter-example per constraint the validator can state, and one per rule it cannot, under `problem/invalid/`.
* [The generated artefacts](generated-artefacts.md) - What the generators write from the schema: `project/`, `src/dpv/datamodel/` and `docs/schema/dpv.yaml`. They are committed and never edited, and the SQL generator is off.
* [Marketing](example-purpose.md) - The purpose `dpv:Marketing` of DPV 2.3, written as a concept of type `DpvPurpose` in the adapt copy's keys. It shows that the domain schema admits a term of a kind.
* [A process with a purpose](example-process.md) - The process `exd:PDH1` of DPV's example E0026, written as a concept of type `DpvResource`. It shows that the domain schema admits a thing a use case describes, with any DPV property.
